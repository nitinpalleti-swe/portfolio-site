How it's built

  1. Find the facts first. A keyword search (BM25) picks the relevant sections of my résumé and project notes; the model answers only from those and cites each one.
  2. Check the model's work. Claude Haiku answers questions; Claude Sonnet writes fit reports, and plain code re-checks every row before you see it.
  3. Safe to leave public. Off-topic requests and prompt injection are refused, with per-visitor rate limits and a daily spending cap.
  4. Measured, not assumed. A test suite with an AI judge and a held-out set it was never tuned on has to pass before deploying.

Decisions I'd defend in an interview

  1. Facts before AI. Timelines, flags, policy eligibility and citations are deterministic and visible without a model.
  2. Fail closed. Unknown source IDs, malformed output, deadlines and rate limits become explicit review-required states — never fake success. [2]
  3. Hold out the holdout. The held-out set is fingerprinted, not consumed, until an independent adapter is ready. [3]

Known limitations by design

  • Synthetic data only — no payment rails, no money movement.
  • Tenant selection is caller-controlled; it is not auth.
  • Vector retrieval uses an offline fixture, not an embedding-quality claim.
  • Bedrock adapter and public demo are gated on access and review. [5]

How I approach applied AI

deterministic →

Make the facts boring

Retrieve, order and validate the evidence in plain code first. The model should summarise facts, not invent them.

contract →

Typed boundaries around the model

Schema-validated requests and responses, source-ID checks, timeouts and budgets. A model is a dependency that can fail like any other. [2]

eval →

Measure before you promote

Versioned dev, held-out and adversarial sets with a gate that blocks release when the evidence isn't there. [3]

human →

Keep a human in the loop

Drafts are versioned, approvals use optimistic concurrency and leave one durable audit event. [4]
